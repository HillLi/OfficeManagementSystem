# 高校办公管理系统（北京大学）设计方案

## 1. 项目概述

### 1.1 项目背景

基于北京大学（PKU）真实行政规章制度，设计并实现一套高校办公管理系统。系统覆盖公文管理、印章管理、会议管理、请示报告/保密管理、差旅审批等核心办公业务流程，集成AI智能审核和AI公文起草两项智能化功能。

### 2.1 整体架构

```
┌─────────────────────────────────────────────────────┐
│                    Vue 3 前端                         │

│  └──┬───┘ └──┬───┘ └──┬───┘ └──┬───┘ └──┬───┘       │
│     └────────┴────────┴────────┴────────┘            │
│              Pinia 状态管理 + Axios                   │
│              Element Plus UI组件库                    │

│  ├──────────────────────────────────────────────┤    │
│  │          DAO 数据访问层                        │    │
```

### 2.2 架构风格

1. **MVC模式**：Controller处理HTTP请求，View由Vue前端承担，Model由Service+Entity承载
2. **三层架构**：Controller（展现层）→ Service（业务逻辑层）→ DAO（数据访问层），层间通过接口解耦

- 普通办公人员默认只能查看本人发起、本人参与审批、本人签收的业务数据。

## 4. 业务模块设计

### 4.1 公文管理

**依据**：《北京大学规章制度管理办法》、《北京大学保密工作规定》

**业务流程**：
```
公文起草 → AI格式校验 → 部门审核 → 部门负责人审批 → 校办审核 → 校级领导签发 → 分发 → 归档
     │                                              │
     └── 退回修改 ←─────────────────────────────────┘
```

**功能清单**：
- 公文模板管理（通知、决定、请示、批复、报告、函等文种模板）
- 在线富文本编辑器起草公文
- AI智能审核公文格式（标题规范、文号格式、正文结构、附件检查）
- AI公文起草助手（根据主题和要点自动生成公文草稿）
- 多级审批流程（支持退回、催办、转办）
- 公文分发与签收
- 公文归档与全文检索
- 保密等级标识（公开/内部/机密/绝密）

### 4.2 印章管理

**依据**：《北京大学印章管理规定》校发〔2017〕41号

**业务流程**：
```
保存用印草稿 → 上传有效材料 → 提交审批 → 部门负责人审批 → 党办校办审核 → 用印登记 → 归还确认
     │                                    │
     └── 退回 ←───────────────────────────┘
```

**功能清单**：
- 印章台账（名称、类型、保管单位、状态）
- 用印在线申请（选择印章、上传材料、说明用途）
- 申请列表返回印章名称和有效材料数量；草稿未具备材料时禁止进入审批流程
- 用印材料真实落盘并支持下载、名称/密级修改及逻辑删除；删除人与删除原因纳入审计
- 分级审批（校级印章需校领导批准，常规用印由部门负责人审批）
- 用印登记簿（日期、申请人、事由、审批人、经办人）
- 印章外带申请（须单位负责人批准）
- 印章移交记录
- 印章状态监控（在库/使用中/外带）

**关键规则（来自北大印章管理规定）**：
- 党办校办是印章综合管理部门
- 严禁在空白纸张上用印
- 各单位须建立用印登记簿，保留10年
- 印章遗失须立即向党办校办和保卫部报告

### 4.3 会议管理

**依据**：《北京大学大型活动安全管理规定》、《北京大学会议费管理暂行办法》

**业务流程**：
```
会议申请 → 会议室预定 → 部门负责人审批 → 会议通知 → 会议签到 → 纪要编写 → 纪要审批 → 归档
```

**功能清单**：
- 会议室资源管理（容量、设备、可用时段）
- 在线预定（冲突检测、自动推荐可用时段）
- 会议通知自动推送（邮件/站内消息）
- 会议签到（支持二维码签到）
- 纪要在线编写和审批
- 会议材料附件管理

### 4.4 请示报告与保密管理

**依据**：《北京大学保密工作规定》、《北京大学党务公开实施办法》

**业务流程**：
```
请示/报告提交 → 保密审查 → 部门负责人审批 → 上级审批 → 批复 → 归档
```

**功能清单**：
- 请示报告在线编写和提交
- 保密等级自动/手动标注（公开/内部/机密/绝密）
- 保密文件借阅审批流程
- 涉密文件访问日志记录
- 文件解密到期提醒

### 4.5 差旅审批

**依据**：《北京大学国内差旅费管理暂行办法》校发〔2019〕252号

**业务流程**：
```
差旅申请 → 行程填写 → 费用预算 → 部门负责人审批 → 财务审核 → 出差 → 报销申请 → 财务审批 → 归档
```

**功能清单**：
- 差旅申请（出发地/目的地/时间/事由）
- 自动计算差旅费标准（城市等级、交通工具等级、住宿标准）
- 多级审批流程
- 差旅报告提交
- 费用报销（发票上传、费用明细）

### 4.6 制度条款到系统规则映射

| 制度依据 | 关键规则 | 系统设计落点 |
|----------|----------|--------------|
| 《北京大学印章管理规定》第二十条、第三十一条 | 印章移交须办理手续；用印登记要求完整、清晰、可追踪、可倒查，登记簿保留10年 | 增加印章移交表、用印登记簿、审批附件和操作审计；归档记录不允许物理删除 |
| 《北京大学印章管理规定》第二十五条 | 校级印章按重大事项、一般事项、常规事项分级审批 | 通过印章台账识别校级/部门印章，以 `matter_level` 动态构建审批路径 |
| 《北京大学保密工作规定》第七条、第八条 | 保密范围包括国家秘密及学校内部事项；国家秘密分为绝密、机密、秘密，内部事项不得擅自扩大知悉范围 | 公文保存 `secrecy_level`、`knowledge_scope`；业务读取、附件和审批历史按登录用户范围过滤 |
| 《北京大学保密工作规定》第二十条、第二十一条 | 禁止通过非保密渠道传递国家秘密载体；禁止非涉密系统处理涉密信息 | AI 调用前判断密级；内部、秘密、机密、绝密以及历史英文等价值均禁止外部 AI 审查 |
| 《北京大学大型活动安全管理规定》第二条、第七条 | 室内大于500人、室外大于100人的活动纳入大型活动，并须提交安全材料 | 会议申请以 `expected_count`、`venue_type` 识别大型活动并校验风险报告、安全方案和应急预案 |
| 《北京大学大型活动安全风险评估办法》第五条 | 大型活动承办方至少提前15个工作日提出风险评估申请 | 大型会议申请自动执行 15 个工作日提前期校验 |
| 《北京大学大型活动安全管理规定》第七条 | 大型活动需提交风险报告、安全方案、应急预案等材料 | 大型活动附件清单作为流程必填项，缺少材料不得提交审批 |
| 《北京大学会议费管理暂行办法》第十二条、第十三条 | 会议费包括住宿费、伙食费、会议室租金等；按会议类别实行综合定额控制 | 会议预算增加会议类别、人数、天数、住宿/伙食/其他费用，自动校验综合定额 |

## 6. AI功能设计

### 6.1 AI公文智能审核

**功能目标**：在公文提交审批前，自动检查公文格式、内容是否符合规范，给出结构化的审核意见和修改建议。

**审核维度**：
- 标题格式：是否符合公文标题规范（如"关于XXX的通知"）
- 文号格式：是否正确（如"校发〔2026〕XX号"）
- 正文结构：是否完整（主送机关、正文、落款、日期）
- 保密等级：根据内容关键词建议合理的保密等级
- 制度引用：引用的制度文件是否存在于北大制度库

**技术实现**：
- 通过策略模式，不同公文类型使用不同的审核Prompt模板
- 调用大模型API（智谱GLM或OpenAI）进行审核
- 返回结构化JSON审核结果，前端渲染为可操作的审核报告

### 6.2 AI公文起草助手

**功能目标**：用户输入公文主题和要点，AI根据北大公文规范自动生成完整公文草稿，解决"不会写、反复退回"的痛点。

**技术流程**：
1. 用户选择文种，输入主题和要点
2. 后端构造Prompt，注入北大公文格式规范、对应文种模板结构、相关北大规章制度条款
3. 调用大模型API生成公文草稿
4. 后处理：格式规范化、自动生成文号、填入日期落款
5. 返回公文草稿，用户可编辑修改后提交审批

**支持的文种**：通知、决定、请示、批复、报告、函、公告

**两个AI功能形成闭环**：
```
[AI起草助手] 生成草稿 → 用户编辑 → [AI智能审核] 检查格式/规范 → 提交审批
```

### 6.3 AI合规与安全边界

- AI功能只提供辅助建议，不替代部门负责人、校办、财务、保卫和校级领导的人工审批。
- 公文、请示报告、会议材料、差旅附件在调用AI前必须进行密级判断。
- `内部` 材料调用外部AI前必须脱敏，并记录调用人、调用时间、输入摘要和模型返回摘要。
- `秘密`、`机密`、`绝密` 材料禁止调用外部AI服务；如需智能处理，应采用本地模型或规则引擎。
- AI生成内容必须保留“由AI生成/辅助生成”的标识，提交审批前由申请人确认。
- AI审核结果以结构化JSON保存，便于复核和测试，不直接覆盖用户原文。

### 6.4 其他智能化功能扩展

| 功能 | 所属模块 | 输入 | 输出 | 设计模式 |
|------|----------|------|------|----------|
| 会议室智能推荐 | 会议管理 | 人数、时间、设备、地点偏好 | 可用会议室排序和推荐理由 | 策略模式 |
| 差旅费用智能校验 | 差旅审批 | 人员类别、出差类型、目的地、费用明细 | 标准金额、超标项、说明建议 | 规则策略 + 适配器 |
| 审批风险提示 | 通用审批 | 金额、密级、事项等级、历史退回记录 | 高风险标签和补充材料建议 | 责任链模式 |

## 7. 设计模式应用

### 7.1 创建型模式

**单例模式** — AI审核服务配置管理
- 全局唯一的AI服务配置（API Key、模型参数）
- Spring Bean天然单例实现

**工厂方法模式** — 公文对象创建
- `DocumentFactory.createDocument(type)` 根据公文类型创建不同的公文对象
- 每种文种对应一个具体工厂

**建造者模式** — 审批流构建
- `ApprovalChainBuilder` 逐步构建复杂的多级审批链
- 支持条件分支和并行节点配置

### 7.2 结构型模式

**代理模式** — 权限控制代理
- `SealServiceProxy` 在印章服务调用前检查用户权限、记录操作日志
- 通过Spring AOP实现

**装饰器模式** — 公文处理增强
- 基础公文处理 → 附加保密检查装饰 → 附加AI审核装饰
- 层层增强处理能力，不修改核心逻辑

**适配器模式** — 多AI服务适配
- `AIReviewAdapter` 统一适配不同大模型API（智谱GLM/OpenAI）
- 对外暴露统一接口，切换AI服务商无需修改业务代码

**组合模式** — 部门和菜单树
- `DeptTreeNode`、`MenuTreeNode` 统一处理学校、院系、科室等层级结构
- 前端导航菜单和后端数据权限范围可复用树形遍历逻辑

**外观模式** — 报表聚合服务
- `DashboardFacade` 对外提供统一统计入口
- 内部聚合公文、印章、会议、差旅等多个服务，降低前端调用复杂度

### 7.3 行为型模式

**责任链模式** — 多级审批流
- 审批请求依次经过：办公人员 → 部门负责人 → 校办 → 校领导
- 每人可批准/退回/转办

**策略模式** — 公文审核策略
- 不同公文类型使用不同审核策略
- 通知类简单审核 vs 合同类严格审核

**观察者模式** — 审批状态通知
- 公文状态变更时，自动通知申请人、下一审批人、抄送人
- 支持邮件和站内信两种通知渠道

**模板方法模式** — 业务处理流程
- `AbstractBusinessProcess` 定义通用流程：提交 → 审核 → 审批 → 归档
- 各业务模块子类实现具体的提交、审核、审批细节

**状态模式** — 业务单据状态流转
- `DocumentState`、`SealApplyState`、`TravelState` 封装 draft、pending、approved、rejected、archived 等状态行为
- 防止在Service中堆叠大量状态判断

### 7.4 个人设计模式落地矩阵

| 成员 | 模块 | 创建型 | 结构型 | 行为型 | 对应类/组件 |
|------|------|--------|--------|--------|-------------|
| 成员A | 公文管理 + AI | 工厂方法 | 装饰器、适配器 | 策略、模板方法 | DocumentFactory、AIProviderAdapter、DocumentReviewStrategy、DocumentProcessTemplate |
| 成员B | 印章管理 + 权限认证 | 单例 | 代理 | 责任链、观察者、状态模式 | SealConfig、SealServiceProxy、SealApprovalChain、SealStatusObserver、SealApplyState |
| 成员C | 会议管理 + 请示报告 | 建造者 | 组合模式 | 模板方法、责任链、观察者 | MeetingBuilder、DeptTreeNode、ReportProcessTemplate、MeetingApprovalChain、MeetingNotifyObserver |
| 成员D | 差旅审批 + 统计报表 | 工厂方法 | 适配器、外观模式 | 策略、观察者 | TravelRuleFactory、TravelStandardAdapter、DashboardFacade、ExpenseStrategy、ReportDataObserver |

每位成员至少包含5种设计模式，并覆盖创建型、结构型、行为型三类。实现时每个成员需在本人模块的JUnit测试中体现至少2个核心模式的行为测试。

| 印章使用汇总 | 可见用印申请数 | oa_seal_log | 当前登录用户职责范围 |
| 会议活动汇总 | 可见会议数、大型活动数 | oa_meeting | 当前登录用户职责范围 |
| 差旅汇总 | 可见差旅数、差旅预算总额 | oa_travel | 当前登录用户职责范围 |
| 月度业务汇总 | 各月可见业务数量 | 核心业务表 | 当前登录用户可见范围 |

### 9.2 展示方式

- 工作台展示个人待办、近期通知、快捷入口和本月业务概览。
- 统计报表页面使用 ECharts 展示折线图、柱状图、饼图和指标卡。
- 报表查询支持按部门、时间范围、业务类型和审批状态筛选。
- 对涉密业务，报表只展示数量和流程状态，不展示正文、附件名称和敏感摘要。

### 10.1 小组 Spring Test

| 测试类 | 覆盖范围 | 重点断言 |
|--------|----------|----------|

### 10.2 个人 JUnit

| 成员 | 测试类 | 覆盖业务规则 |
|------|--------|--------------|
| 成员A | DocumentReviewStrategyTest、AIProviderAdapterTest | 不同文种审核策略、AI返回JSON解析、涉密材料禁止外部AI |
| 成员B | SealApprovalChainTest、SealApplyStateTest | 印章分级审批、状态流转、用印登记完整性 |
| 成员C | MeetingBuilderTest、LargeActivityRuleTest | 会议对象构建、室内/室外人数阈值、安全材料必填 |

### 10.3 AI接口测试策略

- 单元测试中使用 Mock AI 客户端，固定返回结构化JSON，避免测试依赖外部网络。
- 集成测试只验证请求构造、脱敏逻辑、密级拦截和结果保存。
- 对AI输出只做格式和风险提示断言，不以生成文本质量作为自动化测试标准。
