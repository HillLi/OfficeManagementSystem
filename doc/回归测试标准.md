# 高校办公管理系统回归测试标准

本文档作为当前系统的功能测试、回归测试和缺陷定位基准。后续无论由开发者、测试人员还是自动化代理执行测试，都应优先以本文档为标准检查页面、按钮、接口、权限、状态流转和核心业务规则。

## 1. 测试目标

好的测试不只验证页面能打开，还要验证系统是否符合业务设计。当前系统的测试目标如下：

1. 验证所有页面、按钮、弹窗、表单、表格、菜单权限可正常工作。
2. 验证公文、用印、会议、差旅、请示报告、公告、邮件等核心业务可以形成闭环。
3. 验证不同角色只能看到和操作自己有权限的数据。
4. 验证关键业务规则在前端和后端都不会被绕过。
5. 验证异常输入、越权访问、状态错误、重复操作会被正确拦截。
6. 验证统计、流程导览、通知、审批记录、附件、审计日志等辅助能力同步正确。
7. 验证内存模式和 MySQL 模式下数据行为一致，重启后持久化数据可恢复。

## 2. 回归测试分级

| 等级 | 范围 | 必须执行场景 |
|---|---|---|
| P0 | 登录、权限、审批流、数据安全、核心闭环 | 每次改动后必须执行 |
| P1 | 每个业务页面的按钮、弹窗、表单、列表刷新 | 每次发版前必须执行 |
| P2 | 图表、导出、页面布局、空状态、提示文案、响应式 | 重要发版或 UI 改动后执行 |
| P3 | MySQL 持久化、外部邮件、浏览器兼容、性能 | 交付、演示或环境切换前执行 |

## 4. 全局测试标准

### 4.1 登录与会话

| 功能点 | 操作 | 预期结果 | 关注点 |
|---|---|---|---|
| 未登录访问业务页 | 直接访问 `/dashboard`、`/documents` 等 | 自动跳转 `/login` | 不能泄露页面数据 |
| 正确账号登录 | 输入账号密码，点击"登录" | 进入工作台，保存 token 和用户信息到 sessionStorage | 菜单按角色刷新，字典加载成功 |
| 错误密码 | 输入错误密码点击"登录" | 显示"用户名或密码错误" | 不进入系统 |
| 空用户名或空密码 | 不填或只填一项点击"登录" | 后端返回错误，页面提示失败 | 不能生成 token |
| 连续登录失败 | 同一账号连续错误 5 次 | 账号锁定 10 分钟，提示"登录失败次数过多，请稍后再试" | 锁定期间即使密码正确也无法登录 |
| 退出登录 | 点击顶部"退出" | token 清除并回到登录页 | 再访问业务接口应 401 |
| token 失效 | 删除 sessionStorage 中的 `oms_token` 后刷新 | 自动跳登录页 | 页面不应停留在旧数据状态 |

### 4.2 菜单与路由权限

| 页面 | 路径 | 可见角色（roleKey） | 不可见角色关注点 |
|---|---|---|---|
| 工作台 | `/dashboard` | 全部登录用户 | 无 |
| 公文管理 | `/documents` | `office_user`、`dept_head`、`school_leader`、`office_admin` | `admin`、`finance_staff`、`security_staff`、`seal_keeper` 不应在菜单看到 |
| 印章管理 | `/seals` | `office_user`、`dept_head`、`school_leader`、`office_admin`、`seal_keeper` | `finance_staff`、`security_staff` 不应在菜单看到 |
| 会议管理 | `/meetings` | `office_user`、`dept_head`、`school_leader`、`office_admin`、`security_staff` | `finance_staff`、`seal_keeper` 不应在菜单看到 |
| 邮件中心 | `/mails` | 全部登录用户 | 无 |
| 差旅审批 | `/travels` | `office_user`、`dept_head`、`school_leader`、`finance_staff` | `office_admin`、`security_staff`、`seal_keeper` 默认不应看到 |
| 请示报告 | `/reports` | `office_user`、`dept_head`、`school_leader`、`office_admin` | `finance_staff`、`security_staff`、`seal_keeper` 默认不应看到 |
| 审批任务 | `/approvals` | `dept_head`、`school_leader`、`office_admin`、`finance_staff`、`security_staff` | `office_user`、`seal_keeper` 默认不应看到 |
| 通知公告 | `/announcements` | 全部登录用户 | 维护入口仅 `admin`、`office_admin` |
| 统计报表 | `/statistics` | 全部登录用户 | 数据范围要按角色控制 |
| 用户管理 | `/admin/users` | `admin` | 非 admin 直接访问路由守卫重定向到 `/dashboard`，后端也应 403 |
| 字典管理 | `/admin/dictionaries` | `admin` | 非 admin 直接访问路由守卫重定向到 `/dashboard`，后端也应 403 |

> **注意**：`admin` 角色在后端 `AuthInterceptor` 中对 `/api/admin/**` 路径有专门的权限拦截，但前端菜单配置中 admin 未显式列入各业务页面的可见角色。如果 admin 需要访问特定业务页面（如公文管理），应在前端菜单配置 `navigation.js` 中为其添加对应路径权限，或确认 admin 通过其他方式（如直接输入 URL）访问时后端是否允许。

### 4.3 通用页面关注点

1. 每个页面刷新后数据能重新加载。
2. 空列表显示空状态，不显示异常堆栈。
3. 新增、修改、审批、删除后，列表和顶部角标要同步刷新。
4. 所有下拉项应显示中文字典标签，不应显示裸 code，除非是调试字段。
5. 所有后端错误应显示为用户可理解的中文提示。
6. 禁用按钮必须真的禁用，不能通过接口绕过。
7. 前端隐藏按钮不等于后端授权，必须用接口越权测试验证。

| 按钮/功能 | 测试点 | 预期结果 |
|---|---|---|
| "公文起草"按钮 | 点击打开起草弹窗 | 弹窗展示标题、文种、密级、正文 |

| 起草弹窗"保存草稿" | 填写完整信息保存 | 列表新增草稿，状态为草稿 |
| 表格"AI 审查" | 对公开公文点击 | 弹出审查结果 |
| 表格"AI 审查"禁用 | 对非公开公文查看 | 按钮禁用或后端阻断 |
| 表格"提交" | 草稿或退回状态点击 | 状态进入部门审批（pending_dept），生成流程实例和待办 |
| 表格"归档" | office_admin/admin 对 approved 公文点击 | 状态变为已归档 |
| 表格"附件" | 打开附件弹窗 | 可新增并查看附件 |
| 附件"保存附件" | 输入文件名、地址、密级 | 附件出现在表格中 |
| 表格"流程导览" | 点击任意公文 | 展示节点、状态、处理角色、处理人、意见、时间 |
| 表格"分发/签收" | office_admin/admin 对 approved 或 archived 公文点击 | 打开分发与签收弹窗 |
| 分发"发起分发" | 选择接收人后提交 | 生成分发记录，接收人收到通知 |
| 分发记录"签收" | 接收人登录点击签收 | 签收时间写入，状态更新 |
| 分发记录"催办" | 管理者对未签收记录点击 | 产生催办通知 |
| "签收记录" | 非管理角色查看已分发公文 | 只能查看记录，不能发起分发 |

业务规则必须测：

1. 只有申请人或 admin 可提交自己的草稿公文。
2. 只有 `office_admin` 或 `admin` 可归档、分发、催办。
3. 只有接收人或 admin 可签收对应分发记录。
4. 只有 approved 或 archived 公文可分发。
5. 接收人和接收部门必须匹配。
6. 退回后再次提交版本号应增加（`rejected` 状态重新提交时 `version` 字段递增，首次从 null 变为 2）。
7. 非公开公文不得调用外部 AI。

**公文审批链**：`pending_dept`（部门负责人）→ `pending_office`（党办校办）→ `pending_leader`（校级领导）→ `approved`

### 5.5 印章管理 `/seals`

| 按钮/功能 | 测试点 | 预期结果 |
|---|---|---|
| "用印申请"按钮 | 点击打开申请弹窗 | 展示印章、用途、份数、事项等级、是否外带 |
| "是否外带"开关 | 打开外带 | 展示外带原因、地点、监督人、预计归还时间 |
| 用印弹窗"取消" | 点击取消 | 不创建草稿 |
| 用印弹窗"保存草稿并上传材料" | 填写必填项保存 | 创建草稿并自动打开材料管理 |
| 外带材料缺失 | 外带但不填原因、地点、监督人或归还时间 | 后端拒绝 |
| 表格"材料管理" | 点击进入材料弹窗 | 显示材料列表和上传区域 |
| 材料"选择文件" | 选择 PDF、DOC、DOCX、JPG、JPEG、PNG | 文件进入待上传列表 |
| 材料"上传材料" | 选择文件和密级后上传 | 材料列表新增，申请材料数增加 |
| 材料"下载" | 点击有效材料下载 | 下载原始文件 |
| 材料"编辑" | 草稿申请人修改材料名称或密级 | 保存成功并刷新 |
| 材料"删除" | 输入删除原因后删除 | 材料逻辑删除，材料数减少 |
| "显示已删除材料" | office_admin/admin 勾选 | 可看到已删除材料及删除状态 |
| "提交审批" | 草稿且材料数大于 0 时点击 | 状态进入审批中 |
| "提交审批"禁用 | 草稿材料数为 0 | 按钮禁用，接口也应拒绝 |
| "登记用印" | `seal_keeper`/`office_admin`/`admin` 对 approved 申请点击 | 状态变为 used，印章状态变为使用中或外带 |
| "确认归还" | `seal_keeper`/`office_admin`/`admin` 对 used 申请点击 | 状态变为 returned，印章状态回到在库 |
| "印章移交"按钮 | `seal_keeper`/`office_admin`/`admin` 可见并点击 | 打开移交弹窗 |
| 移交"登记移交" | 选择印章、接收人、监督人、凭证 | 生成移交记录 |
| "流程导览" | 点击任意申请 | 展示用印流程节点 |

业务规则必须测：

1. 用印草稿必须至少有一份有效材料才能提交。
2. 已删除材料不能计入有效材料数，不能继续下载。
3. 草稿阶段仅申请人可上传、编辑材料。
4. `office_admin`/`admin` 可查看已删除材料。
5. 非 `seal_keeper`、`office_admin`、`admin` 不可登记用印、确认归还、移交。
6. 校级印章进入 office 审核路径，普通印章进入部门审核路径。
7. 重大事项和校级印章的审批路径要区别普通事项。
8. 外带归还逾期时应记录逾期归还审批记录。

**用印审批链（4种）**：

| 条件 | 审批链 |
|---|---|
| 校级印章 | `pending_office` → `approved` |
| 普通印章 | `pending_dept` → `approved` |
| 普通印章 + 重大事项 | `pending_dept` → `pending_office` → `approved` |
| 校级印章 + 重大事项 | `pending_office` → `pending_leader` → `approved` |

| "发布为公告" | 全员确认后（`minutes_confirmed`）组织者点击 | 生成公告并归档会议 |
| "直接归档" | 全员确认后（`minutes_confirmed`）组织者点击 | 不生成公告，会议归档 |
| "流程导览" | 点击会议 | 展示流程节点 |

业务规则必须测：

1. 参会人不能为空。
2. 记录员不能为空，且必须在参会人中。
3. 会议室必须存在、启用且容量足够。
4. 同一会议室时间段不能重叠。
5. 大型活动必须提前至少 15 个工作日申请。
6. 大型活动必须填写风险报告、安全方案、应急预案。
7. 会议费用分项合计必须等于预算。
8. 预算不得超过会议类型标准上限。
9. 只有记录员可填写纪要（后端校验）。
10. 只有参会人可确认纪要，不能重复确认（后端校验 `isMinutesConfirmed`）。
11. 全员确认后（`minutes_confirmed`）才可发布公告或直接归档。
12. 只有组织者可发布、归档、催办（后端校验 `organizerId`）。

**会议审批链**：

| 条件 | 审批链 |
|---|---|
| 普通会议 | `pending_dept`（部门负责人）→ `approved` |
| 大型活动 | `pending_security`（保卫人员）→ `pending_dept`（部门负责人）→ `pending_leader`（校级领导）→ `approved` |

## 6. 通用组件专项测试

### 6.1 流程导览弹窗

1. 从公文、用印、会议、差旅、请示报告、审批任务、流程实例、审批记录进入导览。
2. 检查当前节点、业务状态、节点类型、处理角色、处理人、意见、处理时间、截止时间显示正确。
3. 空流程或无权限业务应显示空状态或错误提示，不应白屏。
4. 时间字段必须格式化为可读时间，不能显示 `[object Object]`。
5. 退回流程应突出 rejected 或当前退回节点。

### 6.2 组织用户树选择器

1. 部门节点展开、用户节点勾选、取消勾选。
2. 只提交用户 ID，不提交部门 ID。
3. 已选用户应以标签显示，可单独移除。
4. 会议参会人、会议记录员、邮件收件人、邮件抄送均应复用并表现一致。
5. 大量用户时页面不应明显卡顿。
6. 组织树数据来源于 `/api/org/tree` 接口，测试时需验证接口返回完整的部门层级和用户节点。

### 6.3 附件与材料

1. 用印材料支持真实文件上传（通过 `/api/workflow/attachments/upload` 接口）。
2. 文件类型限制为 PDF、DOC、DOCX、JPG、JPEG、PNG。
3. 单文件大小限制 20 MB。
4. 下载有效材料成功（通过 `/api/workflow/attachments/{id}/download` 接口），删除材料后不能继续下载。
5. 删除必须记录删除原因、操作人、删除时间。
6. 非用印业务当前不支持真实上传时，应返回清晰错误。

| 字典 | `GET /api/dictionaries`、`GET /api/dictionaries/version`、`GET/POST/PUT /api/admin/dictionaries/types`、`GET/POST/PUT /api/admin/dictionaries/types/{dictType}/items` | 字典目录、版本、类型和项目管理 |

接口通用断言：

1. 未带 token 访问 `/api/**` 返回 401。
2. 带无权限角色 token 返回 403 或业务错误。
3. 请求成功统一返回 `success=true`。
4. 请求失败统一返回 `success=false` 和中文 message。
5. 非 GET 成功后前端应触发业务刷新事件。
6. 敏感实体不应返回密码明文、外部邮件密钥、涉密正文给无权用户。

## 8. 核心流程闭环用例

### 8.1 公文闭环

1. user（`office_user`）起草公开公文并保存草稿。
2. user 执行 AI 起草和 AI 审查。
3. user 提交审批 → 状态变为 `pending_dept`。
4. head（`dept_head`）在审批任务同意 → 状态变为 `pending_office`。
5. office（`office_admin`）在审批任务同意 → 状态变为 `pending_leader`。
6. leader（`school_leader`）在审批任务同意 → 状态变为 `approved`。
7. office 归档 → 状态变为 `archived`。
8. office 分发给 user 或其他用户。
9. 接收人签收。
10. 验证状态、流程导览、审批记录、通知、统计全部更新。

### 8.2 用印闭环

1. user（`office_user`）创建用印草稿。
2. user 上传材料。
3. user 提交审批。
4. 按审批链流转（普通印章：`pending_dept`；校级印章：`pending_office`；重大事项可能加 `pending_leader`）。
5. keeper（`seal_keeper`）登记用印。
6. keeper 确认归还。
7. keeper 创建印章移交记录。
8. 验证材料数、印章状态、流程导览、审批记录、审计日志。

### 8.3 会议闭环

1. user（`office_user`）创建普通会议，选择参会人和记录员。
2. head（`dept_head`）审批通过 → 状态变为 `approved`。
3. 记录员填写纪要 → 状态变为 `minutes_pending`。
4. 参会人逐个确认纪要 → 全员确认后状态变为 `minutes_confirmed`。
5. 组织者发布为公告或直接归档 → 状态变为 `archived`。
6. 验证我参与的会议、确认进度、公告生成、日程、统计。

### 8.4 大型活动闭环

1. 创建室内超过 500 人或室外超过 100 人的会议。
2. 验证提前不足 15 工作日被拒绝。
3. 验证缺风险报告、安全方案、应急预案被拒绝。
4. 填写完整材料并提交 → 状态进入 `pending_security`。
5. security（`security_staff`）审批 → `pending_dept`。
6. head（`dept_head`）审批 → `pending_leader`。
7. leader（`school_leader`）审批 → `approved`。
8. 验证大型活动标记和统计。

### 8.5 差旅闭环

1. user（`office_user`）创建差旅申请 → 状态变为 `pending_dept`。
2. head（`dept_head`）审批通过 → 状态变为 `pending_finance`。
3. finance（`finance_staff`）审核通过 → 状态变为 `approved`。
4. user 提交报销。
5. finance 复核通过 → 差旅归档。
6. 验证超标说明、票据附件、状态归档、统计金额。

### 8.6 请示报告闭环

1. user（`office_user`）提交内部请示报告 → 状态变为 `pending_secret_review`。
2. office（`office_admin`）执行保密审查 → 状态变为 `pending_dept`。
3. head（`dept_head`）审批 → 状态变为 `pending_leader`。
4. leader（`school_leader`）审批 → 状态变为 `approved`。
5. office 或 leader 批复归档。
6. 验证密级、数据范围、流程导览、审批记录。

### 8.7 邮件闭环

1. user 给 security 发邮件，并抄送 head。
2. security 登录查看收件箱，打开详情自动已读。
3. head 登录查看抄送邮件。
4. 无关用户尝试访问详情接口，应被拒绝。
5. 发件人查看已发送详情和外部投递状态。
6. 发件人或 admin 执行重试邮件。

### 8.8 公告闭环

1. office（`office_admin`）创建公告草稿。
2. office 发布全校公告。
3. user 在公告列表和工作台看到公告。
4. office 撤回公告。
5. user 不再看到该公告。
6. 创建指定部门公告，验证跨部门用户不可见。

## 9. 设计与代码结构测试

当前项目强调设计模式落地，因此测试还应覆盖设计行为，而不是只覆盖接口。

| 设计点 | 实际类名 | 测试关注 |
|---|---|---|
| 工厂模式 | `DocumentFactory` | 不同文种创建出的公文字段正确 |
| 策略模式 | `DocumentReviewStrategy`（含 `DefaultDocumentReviewStrategy`、`ReportDocumentReviewStrategy`）、`TravelExpenseStrategy` | 不同文种、不同差旅标准使用不同规则 |
| 装饰器 | `AiReviewDecorator`、`SecrecyCheckDecorator`（基于 `BaseDocumentProcessor`） | 涉密材料阻断外部 AI，公开材料允许审查 |
| 适配器 | `AiProviderAdapter`（含 `MockAiProviderAdapter`） | AI 草稿和审查返回结构可被系统消费 |
| 责任链 | `ApprovalChainFactory`（含 `DeptHeadHandler`、`OfficeAdminHandler`、`SchoolLeaderHandler`、`SecurityHandler`、`FinanceHandler`、`SecretReviewHandler`） | 不同业务、状态、事项等级流向正确审批角色 |
| 状态模式 | `StateFactory`（含 `DraftState`、`PendingState`、`ApprovedState`、`RejectedState`，基于 `BusinessState` 接口） | 同意、退回、归档的状态转移正确 |
| 观察者 | `StatusChangeNotifier`（含 `ApplicantNotificationListener`、`NextApproverNotificationListener`） | 状态变化后通知申请人或下一处理人 |
| 建造者 | `MeetingBuilder` | 会议对象字段完整，默认值正确 |
| 组合模式 | `DeptTreeBuilder`、`DeptTreeNode` | 组织树层级和用户节点正确 |
| 外观模式 | `DashboardFacade`（`DashboardService` 中聚合） | 工作台聚合统计不泄露无权数据 |
| 代理/权限控制 | `BusinessAccessService` | 所有敏感操作都经过后端权限校验 |
| 模板方法 | `AbstractBusinessService`（含 `DocumentWorkflowService`、`SealWorkflowService`） | 通用业务流程模板被正确复用 |

## 11. 安全专项测试

1. 未登录访问任意 `/api/**` 应被拒绝。
2. 普通用户不能访问 `/api/admin/**`、`/api/auth/users`、`/api/workflow/audit-logs`。
3. 普通用户不能审批非本人职责的任务。
4. 部门负责人不能审批其他部门任务。
5. 非收件人不能查看邮件详情。
6. 非接收人不能签收公文。
7. 非申请人不能提交他人的公文、用印草稿、差旅报销。
8. 非 `seal_keeper`/`office_admin`/`admin` 不能登记用印、归还、移交。
9. 非 `office_admin`/`admin` 不能维护公告。
10. 涉密或内部材料不能调用外部 AI。
11. 后端返回不得包含密码明文。
12. CSV 导出不得包含无权敏感明细。

## 13. 缺陷判定标准

满足以下任一条件即应记录 bug：

1. 用户可见功能无法完成或结果错误。
2. 按钮点击无反应且无提示。
3. 前端允许操作但后端拒绝，且页面没有清晰提示。
4. 后端允许越权操作。
5. 状态流转跳过必要节点。
6. 业务规则未拦截非法输入。
7. 页面显示裸 code、乱码、NaN、undefined、空白弹窗。
8. 新增、审批、删除后列表或角标不刷新。
9. 统计数据与业务数据不一致。
10. 涉密、附件、邮件、用户密码等敏感数据泄露。
11. 刷新页面后状态丢失或角色菜单错乱。
12. MySQL 模式下重启后数据丢失。

## 14. 回归通过标准

一次完整回归至少应满足：

1. P0 用例全部通过。
2. 主要 P1 页面按钮和弹窗全部通过。
3. 后端测试（`mvn test`）、前端测试（`npm run test`）、前端构建（`npm run build`）全部通过。
4. 每个角色至少登录一次，并验证菜单和核心数据范围。
5. 至少完成公文、用印、会议、差旅、请示报告、邮件、公告七条闭环中的五条；发版前应全部完成。
6. 所有发现的 P0/P1 缺陷已修复并重新验证。
7. 测试报告记录测试日期、环境、命令、通过项、失败项、截图或日志证据。

## 15. 后续维护规则

1. 新增页面时，必须在本文档添加页面测试清单。
2. 新增按钮时，必须在对应页面表格中添加按钮测试点。
