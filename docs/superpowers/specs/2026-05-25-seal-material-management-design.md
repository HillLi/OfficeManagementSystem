# 印章名称展示与用印材料管理设计

**日期**：2026-05-25
**项目**：高校办公管理系统
**范围**：印章管理中的用印申请记录展示、真实材料上传、材料增删改查、逻辑删除与审计追溯。

## 1. 背景与目标

当前用印申请已经绑定 `sealId`，但列表只展示数字编号，用户无法直接识别所申请的具体印章。材料方面，目前申请仅保存 `materialUrl` 路径字符串；通用附件能力只有新增和查询，印章页面也未接入，无法形成可追溯的材料管理闭环。

本次建设目标：

- 用印申请列表直接展示真实印章名称。
- 将用印材料从单一地址字段升级为真实文件上传与受控下载。
- 支持材料查询、新增、元数据修改和逻辑删除。
- 将材料权限、状态限制、审计日志和 MySQL 持久化纳入现有流程。

## 2. 选择方案

采用“扩展通用附件能力，并接入 `seal` 业务”的方案。

原因：

- 现有 `Attachment`、`WorkflowService` 与数据范围控制已经具备基础结构，可在其上补齐真实文件与 CRUD。
- 印章材料、公文附件和差旅票据能够共享一致的下载、审计和存储约束。
- 避免新增一套与通用附件重复的专用文件机制。

保留现有 `materialUrl` 作为历史数据兼容字段；新创建和维护的用印材料以附件清单为业务事实来源。

## 3. 页面设计

### 3.1 用印申请表单

- 表单保留“印章”选择器，使用 `sealName` 展示可选印章。
- 移除将文件路径作为主要材料录入方式的交互，改为草稿创建后进入“材料管理”窗口上传实际文件。
- 页面明确显示材料数量；无有效材料时不允许提交审批。

### 3.2 用印办理记录

- “印章”列展示真实名称，例如“北京大学行政印章”“信息科学技术学院公章”，不再展示裸 `sealId`。
- 增加“材料”列，展示有效材料数量。
- 增加“材料管理”操作，用户在权限范围内可查看材料清单并执行允许的操作。

### 3.3 材料管理窗口

清单展示：

| 字段 | 说明 |
|------|------|
| 材料名称 | 用户可理解的文件名称 |
| 类型 | PDF、Word、图片等 MIME 类型 |
| 大小 | 文件字节大小的友好展示 |
| 密级 | 公开、内部、秘密等 |
| 上传人 / 上传时间 | 留痕信息 |
| 状态 | 有效或已删除；已删除信息仅管理角色可查看 |

允许操作：

- 上传材料：选择本地文件并提交。
- 下载材料：经权限校验后获取实际文件。
- 编辑材料：修改材料名称与密级，不修改原文件内容。
- 删除材料：执行逻辑删除，文件和删除记录均保留用于审计。

## 4. 业务流程与状态

当前申请创建即进入审批，无法严格执行“审批前必须具备真实材料”。因此新增草稿提交步骤：

```text
新建用印申请草稿 draft
  -> 上传至少一份有效材料
  -> 提交审批 pending_dept / pending_office
  -> 审批通过 approved
  -> 登记用印 used
  -> 确认归还 returned
```

规则：

- 草稿阶段：申请人可上传、修改或删除本人申请的材料。
- 提交审批：至少存在一份未删除的材料，否则拒绝提交。
- 审批中：申请人可补充材料；已上传材料不得由申请人修改或删除，防止审批依据被替换。
- 审批通过、已用印或已归还：申请人仅可查看和下载，不可修改或删除。
- `office_admin`、`admin` 可按职责处理材料逻辑删除；删除必须记录操作人与原因。
- 审批人、印章保管人以及可查看该申请的管理角色，可查看和下载对应材料。

历史兼容：

- 已存在、仅有 `materialUrl` 的历史申请仍可展示旧材料地址。
- 历史申请不会因未迁移附件而被重新阻断已有状态；用户可补充上传正式材料。

## 5. 后端接口

### 5.1 用印申请

| 方法 | 地址 | 说明 |
|------|------|------|
| POST | `/api/seals/applications` | 新建草稿申请，初始状态为 `draft` |
| POST | `/api/seals/applications/{id}/submit` | 校验有效材料后进入既有审批链 |
| GET | `/api/seals/applications` | 返回申请清单，并补充 `sealName` 与有效材料数量 |

### 5.2 附件通用能力扩展

| 方法 | 地址 | 说明 |
|------|------|------|
| POST | `/api/workflow/attachments/upload` | `multipart/form-data` 上传真实文件并绑定 `bizType=seal`、`bizId` |
| GET | `/api/workflow/attachments?bizType=seal&bizId={id}` | 查询有权限查看的材料清单 |
| GET | `/api/workflow/attachments/{id}/download` | 权限校验后下载材料 |
| PUT | `/api/workflow/attachments/{id}` | 修改材料名称与密级 |
| DELETE | `/api/workflow/attachments/{id}` | 请求体携带 `reason`，逻辑删除材料并写入审计记录 |

上传接口不接受前端提供服务器存储路径；后端生成受控文件名和存储地址。

文件约束：

- 支持 PDF、DOC、DOCX、JPG、JPEG、PNG 文件。
- 单个文件最大 `20 MB`。
- 前后端均提示允许类型和大小限制，后端为最终校验点。

## 6. 数据模型与存储

扩展通用附件表和模型：

| 字段 | 用途 |
|------|------|
| `file_name` | 展示名称 |
| `original_name` | 原始上传文件名 |
| `file_url` | 受控下载标识或兼容读取地址 |
| `storage_path` | 服务端内部实际存储路径 |
| `file_size` | 文件大小 |
| `content_type` | MIME 类型 |
| `secrecy_level` | 材料密级 |
| `uploader_id` | 上传人 |
| `deleted` | 逻辑删除标记 |
| `deleted_by` | 删除操作人 |
| `deleted_at` | 删除时间 |
| `delete_reason` | 删除原因 |

存储约束：

- 上传根目录通过后端配置项指定，默认位于运行目录之外的持久化上传目录。
- 数据库不向前端返回 `storage_path`；客户端下载必须经过受权接口。
- 删除操作只标记记录和记录审计，不物理删除原始文件。
- MySQL 初始化脚本支持为已有数据库增量增加字段，保持重复执行安全。

## 7. 权限与审计

- 上传、查看、下载、编辑、删除均先校验用户是否可访问关联的用印申请。
- 申请人只能操作自己的草稿材料，或在审批中补充材料。
- 审批人员和印章保管人只有查看和下载权限，除非同时具备管理角色。
- 管理删除记录必须保存操作人、时间、删除原因，并写入审计日志。
- 下载、上传、编辑、删除均写入 `seal` 业务审计记录；涉密材料的下载不在日志中写入文件内容。

## 8. 错误处理

- 非允许类型或超过 `20 MB` 的文件：拒绝上传并返回明确提示。
- 无材料提交审批：返回“请至少上传一份有效用印材料后再提交”。
- 越权查看、下载或修改：返回 `403`。
- 下载已删除材料：普通用户返回不可用；管理角色仅能查看删除元数据，默认也不得直接下载已删除文件。
- 物理文件缺失：返回文件不可用错误，并记录审计异常，避免假装下载成功。

## 9. 测试与验收

### 9.1 后端自动化测试

- 用印申请返回真实 `sealName`，并按权限过滤列表。
- 新申请初始为 `draft`，没有有效材料时提交失败。
- 上传真实文件后可提交审批，并返回有效材料数量。
- 材料下载返回原始内容且拒绝越权访问。
- 草稿阶段允许编辑与逻辑删除；审批中和完成后限制申请人改删。
- 管理角色逻辑删除后，材料不再出现在普通查询中，删除字段和审计记录存在。

### 9.2 MySQL 验证

- 初始化脚本重复运行通过，新附件字段能够写入。
- 上传、逻辑删除和删除审计信息落库。
- 重启 `mysql` profile 服务后，材料清单、状态和印章名称仍可读取。

### 9.3 前端与浏览器验收

- 用印办理记录可直接识别印章名称。
- 申请草稿上传材料后方可提交审批。
- 材料窗口完成上传、下载、编辑和逻辑删除操作。
- 不同状态下按钮显示和禁用规则符合权限设计。
- 页面操作期间无控制台错误。

## 10. 变更边界

本次实现聚焦用印申请和通用附件基础能力，不包括：

- 文件在线预览或在线编辑；
- 病毒扫描、OCR 或电子签章；
- 已删除材料的物理清理任务；
- 对历史 `materialUrl` 文件自动搬迁或内容校验。
