# 高校办公管理系统符合性修复设计

## 1. 目标与决策

本轮修复以 `doc/2026-05-25.md` 发现的问题为基线，将当前项目修到可按需求文档与已核验制度规则验收的状态。

已确认的核心决策如下：

1. 保留现有 `Vue 3 + Spring Boot 2.5.6 + Spring JDBC + MySQL + PBKDF2` 技术基线，不在本轮迁移到 MyBatis-Plus、Sa-Token 或 BCrypt。
2. 将 `doc/设计.md` 与部署文档修订为实际架构和可复核制度来源，代码行为优先满足业务与合规要求。
3. 先修严重授权和真实 MySQL 启动问题，再补齐制度规则与前端办理闭环。
4. 所有缺陷修复必须由回归测试驱动：后端接口和服务测试先失败、再通过；前端至少通过构建与界面流程验证；MySQL 以初始化后启动和持久化回读验证。

## 2. 修复范围

### 2.1 纳入本轮

| 领域 | 本轮交付 |
| --- | --- |

### 2.2 不纳入本轮

以下事项不作为本轮阻断条件，避免把合规修复扩展为框架重写：

- Spring Boot 大版本升级。
- MyBatis-Plus 或 Sa-Token 替换当前 JDBC 与认证拦截器。
- BCrypt 替换当前已使用的 PBKDF2 密码方案。
- 引入真实外部 AI 模型；AI 仍以现有适配器/模拟能力验证调用限制。
- 与报告缺陷无直接关系的大规模页面重设计。

## 3. 权限与保密设计

### 3.1 统一授权边界

后端新增集中式业务授权服务，由各业务服务调用，不依赖前端隐藏按钮实现安全控制。所有拒绝操作统一返回业务禁止错误，并写入必要审计记录。

| 业务动作 | 允许角色/主体 | 拒绝规则 |
| --- | --- | --- |
| 创建/查看本人公文 | 发起人 | 非本人且无流程职责不得查看正文或附件 |
| 提交公文 | 当前草稿发起人 | 财务、保卫、印章保管人等不得代提交 |
| 审批公文 | 当前待办对应角色或管理员 | 不处于当前节点的角色不得处理 |
| 归档公文 | `office_admin` 或 `admin` | 领导、财务及发起人不得直接归档 |
| 查询附件/审批历史 | 业务发起人、当前/已参与审批人、相应管理角色；涉密时按知悉范围进一步收缩 | 无业务关系人员不得读取 |
| 归档会议纪要 | 会议组织者、`office_admin` 或 `admin` | 财务等无关人员不得归档 |
| 批复归档请示 | `office_admin`、`school_leader` 或 `admin`，且流程已批准 | 财务等无关角色不得批复 |
| 发起差旅报销 | 差旅申请人本人或 `admin` | 财务人员只能审核，不得代替申请人报销 |
| 用印登记与归还 | `seal_keeper`、`office_admin` 或 `admin` | 其他岗位不得登记 |

### 3.2 涉密访问与 AI

1. `公开` 数据按普通业务范围访问。
2. `内部`、`秘密`、`机密`、`绝密` 数据的附件和业务详情只对发起人、实际审批责任人、授权管理岗位开放，并对读取动作记录访问审计。
3. `秘密`、`机密`、`绝密` 内容禁止进入 AI 起草和 AI 审查。
4. `内部` 内容不得直接提交 AI；本轮采用明确拒绝而非自动脱敏，以提供可验证且不误泄露的最小合规行为。
5. `公开` 内容的 AI 起草/审查要记录操作日志，包括用户、业务类型、业务编号和动作类型，不记录完整敏感正文。

### 3.3 登录会话与统计数据范围

1. Token 增加过期时间，访问过期 Token 返回未登录；退出登录时服务端注销当前 Token。
2. 普通办公人员只能查看本人发起事项的首页统计和报表数据。
3. 部门负责人只能查看本人和本部门事项；专项管理岗位仅查看其职责范围内的数据；管理员可查看全局管理汇总，但涉密正文和附件仍服从知悉范围规则。
4. 导出使用与页面查询相同的数据范围，不提供绕过权限的全量下载。

## 4. 业务闭环与制度规则落地设计

### 4.1 公文生命周期

- 草稿仅发起人可以编辑与提交；被退回公文可修改形成新版本再次提交，保留版本号及退回意见。
- 审批通过后由党办校办归档或进入分发；分发记录接收部门/人员和分发时间。
- 接收人可进行签收，系统保存签收时间；未签收记录可由有管理职责的人员发起催办并形成通知及审计日志。
- 公文附件、版本、审批意见、分发和签收数据均受密级与知悉范围控制。

### 4.2 大型活动

- 判定阈值保持为室内人数大于 `500` 或室外人数大于 `100`。
- 判定为大型活动时，必须保留风险报告、安全方案、应急预案三类材料校验。
- 新增提前期校验：提交时间到活动开始日期必须至少覆盖 `15` 个工作日；周六、周日不计入工作日，暂不引入法定节假日表。
- 不满足提前期时拒绝创建，并给出清晰的业务提示。

### 4.3 印章

| 印章范围/事项等级 | 审批路径 |
| --- | --- |
| 部门印章 + 常规事项 | 部门负责人审批 |
| 部门印章 + 一般/重大事项 | 部门负责人后增加党办校办审批 |
| 校级印章 + 常规/一般事项 | 党办校办审批 |
| 校级印章 + 重大事项 | 党办校办后增加校级领导审批 |

新增印章移交记录，保存印章、移交人、接收人、监督人、时间、材料地址及备注；移交仅允许印章保管人、党办校办或管理员操作，不物理删除历史记录。外带用印必须保存外带原因、地点、监督人和预计归还时间。

### 4.4 会议费用

会议申请新增住宿费、伙食费、场地/会议室费用和其他费用字段，并保留总预算字段。校验时以分项合计与会议类型综合定额进行比对；分项合计与提交总额不一致时拒绝。

### 4.5 差旅费用与报销

- 继续使用人员类别、出差类型、目的地和天数计算参考标准，但运行时标准应从标准数据加载，避免仅靠写死常量。
- 报销必须由原申请人提交实际金额和票据附件。
- 若实际费用超过系统核算的上限，必须提交超标准说明，进入财务复核并留档。
- 财务复核通过后状态进入 `archived`，完成审批、报销、归档闭环。

## 5. 数据与 MySQL 设计

### 5.1 现有表修订

| 表 | 增补内容 |
| --- | --- |
| `oa_document` / `oa_report` | `secret_until`（可空），保留 `secrecy_level` 与 `knowledge_scope` |
| `oa_document` | 版本号、分发/签收状态与归档信息，支持退回后再提交 |
| `oa_seal_log` 或用印申请表 | 事项等级、外带原因、外带地点、监督人、预计归还时间 |
| `oa_meeting` | 分项费用字段和大型活动审批日期校验所需数据 |
| `oa_travel` | 票据地址、超标说明、归档时间 |
| `sys_operation_log` | 支持访问审计和 AI 调用审计的动作类型/详情 |

### 5.2 新增表

| 表 | 用途 |
| --- | --- |
| `oa_seal_transfer` | 用印移交记录，保留不可删除的追踪链 |
| `oa_document_distribution` | 公文分发、签收及催办追踪记录 |

现有 `schema.sql` 中已声明但数据库缺失的 `sys_attachment`、`sys_operation_log`、`sys_notification`、`oa_flow_instance`、`oa_flow_task`、标准表必须通过可重复执行脚本落地到已有库。

### 5.3 初始化和迁移策略

1. `backend/sql/schema.sql` 保持可重复执行，既能初始化空库，也能补全已有测试库缺少的表。
2. `backend/sql/data.sql` 维持幂等种子写入。
3. `backend/scripts/init-mysql.ps1` 的默认连接参数与 `application-mysql.properties` 一致，文档同时说明可通过参数覆盖密码。
4. 回归测试在可控测试库执行脚本后，以 `mysql` profile 启动应用，完成登录、创建数据、数据库查询回读、重启后再次读取的验证。

## 6. 前端操作闭环设计

### 6.1 审批中心

`Approvals.vue` 在“我的待办”中为当前可办理任务提供 `同意` 与 `退回` 操作。操作后刷新待办、流程实例、审批历史和通知，错误信息直接展示后端禁止原因。

### 6.2 印章管理

`Seals.vue` 为审批通过或已使用的申请提供对应的 `登记用印`、`确认归还` 操作；为有权限岗位提供移交记录表单和移交历史列表。外带申请展示必填信息并禁止遗漏提交。

### 6.3 表单补充

- 公文列表和详情提供受权限控制的分发、签收、催办操作，并显示版本及签收状态。
- 会议申请增加分项费用和大型活动提示字段。
- 差旅报销要求录入票据地址及超标说明（发生超标时）。
- 公文/报告涉密状态在列表和详情中明确显示，AI 操作在不允许时禁用并显示原因。

前端展示只改善办理体验，所有权限和规则判定仍以后端为准。

### 6.4 统计与导出

补齐按模块汇总的业务报表视图，至少包含公文办理、印章使用、会议/大型活动、请示和差旅费用五类统计。报表与导出结果依据当前登录角色过滤数据范围，并避免输出无权限查看的涉密内容。

## 8. 测试与验收设计

### 8.1 后端回归测试

先添加会失败的测试，再实现修复：

| 测试组 | 必测行为 |
| --- | --- |
| 授权回归 | 财务不得提交或归档他人公文；不得读取涉密附件/审批历史；不得归档会议纪要、批复报告、代提交报销 |
| 会话与数据范围 | 退出后的 Token 失效；过期 Token 被拒；普通人员不能读取其他人的全局统计或导出 |
| 保密与 AI | 内部及以上密级 AI 操作被拒绝；允许的公开 AI 动作产生审计记录 |
| 公文闭环 | 退回形成新版本；仅授权人员分发/签收/催办；流程记录和通知可追溯 |
| 大型活动 | 501 人室内活动提前不足 15 工作日被拒；满足提前期与材料时进入安全审批 |
| 印章 | 不同事项等级生成不同审批路径；无权限移交被拒；移交记录可读取 |
| 差旅 | 无票据报销被拒；非本人报销被拒；超标缺说明被拒；财务复核后归档 |
| MySQL | 初始化后的库具备流程及移交表；`mysql` profile 可启动并回读持久化数据 |

### 8.2 前端与端到端验证

- `npm run build` 必须通过。
- 使用可用的浏览器自动化或用户可见交互测试完成：登录/注销、公文提交审批分发签收、印章办理、会议归档、报告批复、差旅报销和报表导出等核心路径。
- 若内置浏览器能力仍受环境阻塞，必须记录阻塞原因，不将源码检查替代为界面验收通过。

### 8.3 完成门槛

本轮只有在以下条件同时满足时才可标记修复完成：

1. 新增安全与制度反例测试由失败转为通过，且原有测试全部通过。
2. 前端构建成功，新增操作入口可完成对应办理路径。
3. 初始化后的 MySQL 测试库可以启动应用并验证持久化回读。
4. 角色数据范围、会话注销、报表导出和公文签收催办均有可复现的验收证据。
5. 设计、接口、初始化和测试报告文档与代码行为一致。
