# 字典中心与业务中文展示设计

**日期**：2026-05-26
**范围**：高校办公管理系统中所有面向用户的业务页面、字典维护能力、前端缓存与现有业务规则兼容。

## 1. 背景与目标

当前公文、印章、会议、差旅、请示报告、审批任务和统计页面会直接展示部分稳定编码，例如 `draft`、`pending_dept`、`document`、`dept_head` 与 `not_distributed`。虽然这些编码适合业务规则、权限和持久化判断，但用户无法直接理解其含义，也难以保证各页面显示一致。

本轮建设一个可维护的字典中心，达成以下目标：

- 数据库统一保存字典分类与选项，作为业务展示选项的唯一维护来源。
- 页面列表以中文说明展示业务编码，不直接暴露流程或权限编码。
- 表单中的枚举项统一采用下拉选择，避免自由输入非法值。
- 前端登录后缓存字典数据，页面使用统一的字典读取方法，降低重复请求。
- 管理员可以在系统管理中维护普通字典，系统关键编码受到保护。
- 流程路由、权限判断和历史数据仍依赖稳定编码，描述修改不得改变规则行为。

## 2. 字典覆盖范围

### 2.1 纳入字典中心的字段

| 字典类型 | 示例编码或现有值 | 页面说明 |
| --- | --- | --- |
| `business_status` | `draft`, `pending_dept`, `approved`, `archived`, `rejected`, `used`, `returned` | 业务单据和流程实例状态 |
| `distribution_status` | `not_distributed`, `distributed`, `received` | 公文分发与签收状态 |
| `biz_type` | `document`, `seal`, `meeting`, `travel`, `report` | 审批任务、流程、审计业务类型 |
| `flow_node` | `pending_dept`, `pending_office`, `pending_security`, `pending_finance`, `pending_secret_review`, `pending_leader` | 当前审批节点展示 |
| `role_key` | `office_user`, `dept_head`, `school_leader`, `office_admin`, `finance_staff`, `security_staff`, `seal_keeper`, `admin` | 处理角色与用户管理 |
| `secrecy_level` | `公开`, `内部`, `秘密`, `机密`, `绝密` | 公文、报告和材料密级 |
| `document_type` | `通知`, `决定`, `请示`, `批复`, `报告`, `函`, `公告` | 公文文种 |
| `matter_level` | `常规事项`, `一般事项`, `重大事项` | 用印事项等级 |
| `seal_type` | 当前印章台账类型值 | 印章类型 |
| `seal_status` | `in_store`, `in_use`, `lent`, `retired` 等 | 印章台账状态 |
| `meeting_type` | `国内管理会议`, `国内业务会议`, `在华举办的国际会议` | 会议类别 |
| `venue_type` | `室内`, `室外` | 活动场地类型 |
| `report_type` | `请示`, `报告` | 请示报告类型 |
| `staff_level` | `一类`, `二类`, `三类` | 差旅人员类别 |
| `travel_type` | `教学科研业务`, `行政管理业务`, `学术交流` | 出差类型 |
| `transport_type` | `飞机`, `高铁一等座`, `高铁二等座`, `火车软卧`, `火车硬卧`, `火车硬座` | 交通工具 |

### 2.2 不作为字典的基础数据

印章、会议室、用户和部门具有独立业务实体与维护生命周期，不写入字典表。需要选择这些数据时，前端应调用对应基础数据接口，以名称下拉选择并提交实体 ID。例如用印选择印章显示印章名称，移交中的接收人与监督人应选择用户姓名而不是直接输入用户 ID。

## 3. 数据库设计

### 3.1 字典分类表 `sys_dict_type`

| 字段 | 类型 | 约束与含义 |
| --- | --- | --- |
| `id` | BIGINT | 主键 |
| `dict_type` | VARCHAR(60) | 分类编码，唯一且稳定 |
| `dict_name` | VARCHAR(100) | 分类中文名称 |
| `system_type` | TINYINT | 是否为系统内置分类 |
| `enabled` | TINYINT | 是否启用 |
| `remark` | VARCHAR(255) | 说明 |
| `updated_at` | DATETIME | 版本校验依据 |
| `created_at` | DATETIME | 创建时间 |

### 3.2 字典项表 `sys_dict_item`

| 字段 | 类型 | 约束与含义 |
| --- | --- | --- |
| `id` | BIGINT | 主键 |
| `dict_type` | VARCHAR(60) | 关联分类编码 |
| `dict_code` | VARCHAR(100) | 提交、持久化和规则判断使用的稳定值 |
| `dict_label` | VARCHAR(100) | 页面显示描述 |
| `sort_order` | INT | 下拉和展示排序 |
| `enabled` | TINYINT | 新业务是否可选择 |
| `system_item` | TINYINT | 是否为流程或权限依赖的内置选项 |
| `remark` | VARCHAR(255) | 业务说明 |
| `updated_at` | DATETIME | 更新时间 |
| `created_at` | DATETIME | 创建时间 |

同一 `dict_type` 下 `dict_code` 唯一。初始化脚本插入本设计列出的当前业务值，并支持重复执行升级。

## 4. 保护与兼容规则

### 4.1 系统内置保护

以下类型属于流程或安全规则依赖的系统字典：`business_status`、`distribution_status`、`biz_type`、`flow_node`、`role_key`、`secrecy_level`。

- 管理员允许修改中文说明、排序和备注。
- 其分类编码与内置选项编码不可修改或删除，系统内置分类不可停用。
- 流程状态、角色、业务类型和密级中的内置项不可被停用，以避免审批流、权限或保密规则失效。
- 后端在管理接口执行上述保护，前端只负责提示和禁用无效操作。

### 4.2 普通业务字典维护

文种、事项等级、会议类别、场地类型、请示报告类型、差旅类别和交通工具允许管理员新增、修改显示说明、调整排序与启用/停用。已被历史单据使用的选项采用停用而非物理删除。

### 4.3 历史数据读取

- 业务详情和列表展示包含启用与停用的字典项，以确保历史值仍能翻译为原说明。
- 新建或编辑表单只提供启用项。
- 对于数据库中存在但字典表尚未识别的历史值，前端回退显示原值，并允许管理员补充字典配置。

## 5. 后端接口与校验

### 5.1 公共查询接口

| 方法 | 地址 | 说明 |
| --- | --- | --- |
| `GET` | `/api/dictionaries` | 查询前端展示所需全部字典类型及字典项，包含停用历史项和当前版本 |
| `GET` | `/api/dictionaries/version` | 返回字典全局版本，用于浏览器缓存轻量校验 |

返回数据按 `dictType` 分组，每项至少包含 `code`、`label`、`enabled`、`sortOrder` 和 `systemItem`。字典服务以分类与字典项中最大的 `updated_at` 生成全局版本字符串；任何维护成功后必须更新时间，使浏览器缓存能够可靠失效。

### 5.2 管理接口

管理员专用接口覆盖：

- 字典分类列表、新增、编辑、启用/停用。
- 指定分类下的字典项列表、新增、编辑、启用/停用。
- 所有维护动作记录操作日志，说明字典类型、选项编码及变更动作。

### 5.3 业务提交校验

业务 Service 在创建或修改请求中校验可配置枚举字段属于对应类型且处于启用状态。包括公文文种/密级、用印事项等级、材料密级、会议场地与类别、请示报告类型/密级、差旅人员类别/业务类别/交通工具。系统工作流内部写入的状态不经过表单选择校验，而是受已有流程逻辑控制。

## 6. 前端架构与页面交互

### 6.1 字典缓存

新增字典 store 与工具方法：

- 应用登录成功后请求 `/api/dictionaries`，保存到 Pinia 内存状态及 `localStorage`。
- 应用刷新时优先加载本地缓存，再调用版本接口；版本不一致时更新完整字典缓存。
- `optionsOf(dictType)` 返回启用且排序后的下拉选项。
- `labelOf(dictType, code)` 返回显示说明；未找到时回退为原值。
- 退出登录时清除与当前会话绑定的内存状态；公共字典缓存可保留版本化副本供下次登录校验。

### 6.2 业务页面改造

| 页面 | 展示改造 | 录入改造 |
| --- | --- | --- |
| 公文管理 | 流程状态、签收状态、密级显示中文说明 | 文种、密级改用字典下拉 |
| 印章管理 | 用印状态、事项等级、材料密级、印章台账状态显示说明 | 事项等级、材料密级使用字典；人员关联使用用户名称选择 |
| 会议管理 | 审批状态、会议类别、场地类型显示说明 | 会议类别、场地类型使用字典下拉 |
| 请示报告 | 类型、密级、状态显示说明 | 类型与密级使用字典下拉 |
| 差旅审批 | 状态、人员类别、出差类型、交通工具显示说明 | 对应字段使用字典下拉 |
| 审批任务 | 业务类型、节点、处理角色、流程状态和审批动作显示说明 | 无自由输入字典值 |
| 统计/看板 | 状态分布图例和筛选值显示说明 | 筛选选项使用字典 |
| 用户管理 | 角色名称显示说明 | 角色选择显示字典说明并提交稳定编码 |

### 6.3 字典管理页面

系统管理导航增加“字典管理”。页面采用分类与字典项的主从布局：

- 分类列表展示编码、名称、状态、系统标记和更新时间。
- 选择分类后展示选项的编码、描述、排序、启用状态、系统标记与操作。
- 新增和编辑普通字典时提供编码、说明、排序、启停与备注输入。
- 系统内置分类或选项锁定编码及受保护操作，并显示“此编码参与流程/权限规则，仅允许调整显示说明与排序”的提示。

## 7. 业务规则一致性

字典中心只负责枚举维护、选择与展示，不替代业务规则引擎：

- 审批路由继续按 `pending_dept`、`pending_office`、`pending_security` 等状态运行。
- 权限判断继续按 `dept_head`、`office_admin`、`admin` 等角色编码运行。
- 保密与 AI 限制继续按密级稳定值判断。
- 制度规则链接对应的是业务条件和流程路径，不因管理员调整中文描述而变化。

因此，字典项标签改为“部门负责人审核中”等更清晰表述后，既能提升可读性，也不会造成文档所要求的审批流程漂移。

## 8. 测试与验收

### 8.1 后端自动测试

- 初始化字典包含当前业务使用的全部关键类型与初始选项。
- 公共查询接口返回分组字典与版本信息。
- 非管理员无法维护字典，管理员能够维护普通字典。
- 系统内置编码不可修改、删除或非法停用。
- 业务提交使用不存在或已停用的可选字典值时被拒绝。
- 停用后的历史字典项仍通过查询接口返回供历史展示。
- MySQL 初始化脚本可重复执行，服务重启后字典维护结果仍持久化。

### 8.2 前端与浏览器验证

- 登录后加载并缓存字典，刷新页面能先使用缓存并按版本更新。
- 公文、印章、会议、报告、差旅、审批和统计页面不再直接向用户展示流程/权限编码。
- 所有枚举录入字段通过字典下拉选择，禁用项不出现在新建选项中。
- 字典管理页面可维护普通项，并正确限制系统内置项操作。
- 当某个未识别历史编码出现时页面回退展示原值，不出现空白或渲染异常。

### 8.3 全量验证顺序

1. 从 `backend/` 执行 Maven 全量测试。
2. 从 `frontend/` 执行前端构建。
3. 执行字典公共/管理接口及核心业务提交的 API smoke test。
4. 使用浏览器验证关键页面展示、下拉选择、缓存刷新和字典维护流程。
5. 因新增数据库表与持久化行为，执行 MySQL 初始化、字典维护、服务重启后的持久化复核。

## 9. 交付边界

本轮交付包括数据库字典表及初始化数据、后端字典查询与管理接口、业务枚举校验、前端字典缓存及字典管理页面、全部面向用户页面的字典展示/选择改造、文档更新和测试报告。审批流程本身与制度规则链接不在本轮重新定义，仅验证其继续使用受保护稳定编码并与当前文档一致。
